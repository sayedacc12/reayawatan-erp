# سنابل · Sanabel ERP

**منصة إدارة الجمعيات الخيرية**

منصة SaaS لإدارة الجمعيات الخيرية: نظام واحد بوحدات مستقلة تتكامل على قاعدة بيانات واحدة
(على فكرة Odoo)، بواجهة عربية بالكامل.

![شاشة الدخول](docs/screenshots/1-login.png)

## المعمارية

- **Modular monolith**: خادم واحد (NestJS) وقاعدة PostgreSQL واحدة، وكل وحدة عمل
  (الأعضاء، التبرعات، المستفيدين، المحاسبة...) مجلد مستقل يعرّف نفسه بملف manifest
  (الاسم، الصلاحيات، القائمة). انظر `backend/src/modules/README.md`.
- **تعدد الجمعيات (Multi-tenant)**: كل جمعية `organization` منفصلة، وكل جدول بيانات يحمل
  `organization_id`، وكل استعلام مقيد بجمعية المستخدم.
- **مستويان للإدارة**:
  - *مدير المنصة*: يضيف الجمعيات ويوقفها ويفعّل الخدمات الإضافية لكل جمعية، ولا يرى بياناتها.
  - *مدير نظام الجمعية*: له كل الصلاحيات داخل جمعيته، ويدير مستخدميها وأدوارها.
- **الصلاحيات**: كل وحدة تعلن صلاحياتها (`donations.receipts.create`)، والأدوار تجمع صلاحيات،
  والمستخدم يأخذ أدوارًا. لا يمكن لمستخدم منح صلاحية لا يملكها. السحب أو الإيقاف يسري فورًا.
- **وحدات اختيارية لكل جمعية**: وحدة بدون `alwaysEnabled` تظهر فقط للجمعيات المفعلة لها
  (مثلًا الموقع ومنصة التبرعات مستقبلًا).

## اشتراكات الجمعيات والعقد الإلكتروني

- **التسجيل**: الجمعية تقدّم طلبها من `/register` (بيانات الترخيص ومستنده، المدير التنفيذي، عضو مجلس الإدارة، حساب مدير النظام)، وتتابعه برابط سري `/register/<token>`.
- **الاعتماد**: مدير المنصة يراجع الطلب (اعتماد / إعادة للاستكمال / رفض)، ويحدد الشاشات المسموحة والقيمة ودورة السداد والمدة والفترة التجريبية، فتُنشأ الجمعية ومدير نظامها وتُولَّد روابطها (`/o/<slug>` و`/portal/<slug>`).
- **الشاشات المسموحة**: كل عنصر في قائمة أي وحدة شاشة. الشاشة المحجوبة تختفي من القوائم وتُسحب صلاحياتها من كل الأدوار.
- **العقد الإلكتروني**: مكتبة بنود (كائنات بعنوان وفقرات ومتغيرات مثل `{{اسم الجمعية}}`) مع مسودة مقترحة وفق الأنظمة السعودية. كل عقد: مسودة ← إرسال ← (طلب تعديل) ← توقيع إلكتروني من `/contract/<token>` يفعّل الاشتراك. يُثبَّت النص وبصمته SHA-256 عند الإرسال.
- **انتهاء التجربة أو الاشتراك** يوقف دخول الموظفين وبوابة المستفيدين تلقائيًا (بتوقيت الرياض).
- **التقارير**: `/platform/reports`.
- اختياري: `PUBLIC_URL=https://sanabelerp.com` ليظهر في روابط نص العقد.

## الدعم الفني ومستويات الخدمة

- ترسل الجمعية طلب صيانة من "الإعدادات والصلاحيات ← الدعم الفني والصيانة" (`/settings/support`) مع مرفق اختياري، وتختار أحد خمسة مستويات.
- مدير المنصة يستقبل الطلبات في `/platform/support` مرتبة بالمستوى ثم أقرب مهلة، ويرد ويُسند ويعدّل المستوى بسبب ويصعّد، مع ملاحظات داخلية لا تراها الجمعية.
- المهل الافتراضية (أول رد / الحل): حرج جدًا 1 س / 4 س، حرج 2 س / 8 س، متوسط 4 س / 24 س، عادي 8 س / 3 أيام، منخفض 24 س / 7 أيام. تُعدَّل مع خطوات التعامل والتصعيد من `/platform/sla`.
- تتوقف المهلة أثناء انتظار رد الجمعية. يظهر تنبيه التصعيد عند تجاوز أي مهلة، أو مرور نصف مهلة الحل في الحرج جدًا.
- بعد الحل تغلق الجمعية الطلب وتقيّمه، أو تعيد فتحه خلال 7 أيام. التقرير في `/platform/reports`.

## التشغيل بـ Docker

```bash
cp .env.example .env        # غيّر JWT_SECRET وكلمات المرور
docker compose up -d --build
# افتح http://localhost:8080 وادخل بحساب مدير المنصة من .env
```

## التشغيل على سيرفر (إنتاج)

أمر واحد بيشغّل النظام مع HTTPS تلقائي. التفاصيل في [deploy/README.md](deploy/README.md).

## التطوير

```bash
# قاعدة البيانات: PostgreSQL 13+ (أو: docker compose up -d db)
cd backend && cp .env.example .env && npm install && npm run start:dev   # http://localhost:3000/api
cd frontend && npm install && npm run dev                                 # http://localhost:5173
```

الاختبارات (تحتاج قاعدة اختبار فارغة `charity_erp_test`):

```bash
cd backend && npm test
```

إضافة جدول أو تعديله: عدّل الـ entity ثم `npm run migration:generate -- src/migrations/<Name>`.
الـ migrations تعمل تلقائيًا عند تشغيل الخادم.
